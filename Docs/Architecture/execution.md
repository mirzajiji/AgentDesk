# Runs, steps and provider execution

Status: persisted run lifecycle, live/replay events and typed stage/step progress are implemented in P1-07a/b. An internal read-only Codex provider is implemented in P1-09b; P1-10 adds the internal policy/approval gate; P1-06b2 adds frozen environment/configuration/policy previews and validated output contracts. P1-12a/b/c implement scoped redaction, evidence storage and Git capture; P1-11a joins them in an internal policy-gated coordinator with interruption recovery. P1-11b adds the signed Mac execution transport and native service; the run UI remains P1-13 work. Every agent or workflow execution creates a Run with explicit workspace/project ownership. Runs record identity, parent run, agent/workflow references, task, status, creation/start/completion times, execution profile, environment, working directory, result/error, artifact references and trace identity.

## State model

Run statuses are queued, running, waitingForApproval, paused, completed, failed and cancelled. The tested transition matrix permits queued → running/waitingForApproval/failed/cancelled; running → waitingForApproval/paused/completed/failed/cancelled; and waitingForApproval or paused → running/failed/cancelled. Terminal states do not reopen, and same-state updates are rejected. A queued run can fail before provider launch, for example during preflight. A rerun creates a new Run rather than rewrites a historical terminal record.

Separate a user pause, approval wait and queued resource wait so the UI explains why progress stopped. Provider loss and process exit are events to interpret, not automatic evidence that a task succeeded. Completion requires an accepted result and required validations.

## Explicit work structure

RunSteps expose meaningful actions such as load requirements, search documentation, inspect repository, analyze tests, implement automation, execute tests, analyze failures and report. A larger stage can group child steps. Stage/step status and measurable progress come from runtime state. Open-ended reasoning displays activity and stages without invented percentages.

Before starting, freeze an effective context snapshot, check scope and policy, run prerequisites, reserve scheduler capacity, create execution records, and launch the selected provider or deterministic tool. Persist safe output/events and result metadata. Release reservations and clean up execution resources on every exit path.

Proposed recovery behavior: on launch, reconcile nonterminal persisted runs against real process/session state. Mark lost execution explicitly; never pretend to resume a provider session that cannot be recovered. Preserve prior output and expose safe rerun/reproduction choices.

## Verification

Test valid and invalid state transitions, timestamp consistency, exactly-once terminalization, duplicate/out-of-order provider events, cancellation before and during execution, approval/rejection/expiry, timeout, coordinator restart and orphan-process handling. Integration tests should execute fake providers emitting partial stdout/stderr and failing at defined boundaries.

## Implemented lifecycle boundary

`RunState` is a shared Core type; the existing persistence name remains a compatibility alias and stored values/schema are unchanged. `RunLifecycleService` in `AgentDeskRuntime` is bound to one exact project and wraps the workspace-bound SQLite store. The internal coordinator owns one service per project and route lifecycle mutations through it. Direct low-level persistence writes are not runtime authorization and must not be used as an alternative execution path.

The service validates scope, current state, expected sequence and a finite timestamp no earlier than the previous event. Each accepted mutation commits its state/event transaction before live delivery. A per-run operation gate spans storage suspension points, preventing another local mutation from overtaking publication or landing between replay and subscription registration. Conflicting same-run operations return `busy`; unrelated runs can proceed independently. Stale database sequences remain protected by SQLite's compare-and-commit check.

No prompt, arbitrary provider output, secret or interpreted result enters this initial state stream. Moving to `completed` represents an authoritative caller's decision; the coordinator verifies output, policy, provider status and required evidence before making that decision. This module alone neither launches a provider nor approves a tool. User-facing execution still requires the native run UI; the signed bridge and service are now implemented.

Shutdown rejects new operations and closes active observers with a distinct `closed` error. Deallocation also finishes observers. Already-entered storage writes may finish durably; shutdown does not rewrite history or pretend that unreconciled provider processes completed. Startup/process reconciliation belongs to the provider coordinator.

## Implemented work plans

`RunWorkPlan` is a validated, versioned operational snapshot with exact project/run identity, stable stage/step IDs, parent-stage relationships, state, timestamps and optional measured units. It is configured once while queued, then updated only while the run is running. Paused/approval-waiting runs cannot advance work. It describes execution facts and does not grant execution permissions or define an executable workflow.

A fixed plan freezes its stage denominator before execution; completed and explicitly skipped stages count toward completion. It does not estimate partial stage completion. An open-ended plan may discover additional stages and always has no overall numerical percentage. Explicit step/stage counters require a known positive total, cannot decrease and cannot change denominator after the first measurement. Future deterministic runners must supply observed counts; provider reasoning must never manufacture them.

Steps require an active parent to start. Completion requires completed/skipped children and any explicit unit measurement to be complete. Failing or cancelling a stage cancels its unfinished children; skipping a stage skips its unfinished children. Run cancellation/failure finalizes unfinished items while preserving already-observed completed/failed states. A run cannot complete with unfinished or failed work. These constraints complement the coordinator's result and policy validation.

Plans allow at most 32 stages and 128 steps, with titles bounded to 160 UTF-8 bytes. JSON decoding validates the same graph/state/measurement invariants as mutations. All timestamps must be finite and chronological; operational writes use canonical SQLite Unix-time precision so live and replayed event values compare exactly. Typed titles are internal caller-supplied labels; arbitrary provider output still requires the separate redaction/event boundary.

The P1-09a internal Mac byte transport now supports bounded stdin, live stdout/stderr chunks and explicit process-exit/signal results. Diagnostics already use it. It has no run authority, filesystem-scope grant or UI/mobile endpoint. P1-09b adds provider-specific request validation, verified read-only roots and bounded event decoding. The coordinator enforces environment policy, redacts observations and validates results; the signed bridge now connects the native service to Codex, while the run UI remains required; see [Codex transport](codex.md).


`ExecutionProvider` returns a cancellable bounded observation stream; it does not mutate persisted lifecycle state. `CodexCLIProvider` currently executes one ephemeral read-only turn per process. Scope is checked before launch and at output/termination boundaries. Its final event requires protocol and process success, but cannot itself authorize the lifecycle service to mark a run complete. The coordinator must bind the effective configuration, policy decision, redacted evidence and output-schema validation to that same run identity. See [provider validation](../Development/p1-09b-validation.md).


The internal `PolicyGate` now prepares allow/review/deny decisions and wraps dispatch with current scope/authority checks and durable one-time approval consumption. It accepts an application-prepared effect, not arbitrary model commands. The coordinator must supply authenticated principals, resolved resources, an immutable effective configuration and the exact payload whose digest was reviewed. Consumed approvals cannot be reused after a failed/cancelled or uncertain attempt. P1-11a joins lifecycle rows and provider observations through this gate. See [policy and review contract](permissions.md).


The provider request can now be constructed directly from a validated effective configuration plus an exact run ID. It preserves scope, agent, environment, selected model and tightened limits. Workspace-write intent is explicitly unsupported by this provider. The selected output schema is sent to Codex and checked again before a completed event; malformed or nonconforming output fails without a successful terminal event. The configuration includes stored policies and a complete fingerprint for later coordinator/action binding. See [configuration rules](configuration.md) and [validation](../Development/p1-06b2-validation.md).

## Implemented local run coordinator (P1-11a)

`RunCoordinator` is an internal, project/environment-bound actor. It consumes validated instruction/configuration previews and a trusted provider adapter; no model or mobile payload constructs execution authority. Read-only execution is the current supported mode. The provider and optional repository capture expose an `ExecutionResource` fingerprint derived from the physical directory's device/inode plus project scope, so matching project labels cannot substitute another directory.

One process-held project lease covers all environments in the trusted operational container. The 0600 regular single-link lock is opened without following links, checked for replacement, and never unlinked on release. Shutdown waits for preparation/launch and active-run cleanup, including concurrent shutdown calls, before releasing ownership. The native caller must retain the coordinator and await shutdown. Dependencies must cooperate with cancellation; preparation factories must finish or throw rather than wait indefinitely. This is coordination among app instances, not protection against a hostile process with the user's OS authority.

Preparation first checks the current policy and authenticated requester, including separately allowed evidence reads. It then resolves the scoped redactor, sanitizes the composed instructions and task, and freezes exact scope/run/agent/environment, configuration/source revisions, resource, actual limits and output contract. The dispatch digest binds the exact sanitized request independently of display redaction of configuration fields. Instruction provenance stores sanitized-content fingerprints; original unsanitized instruction hashes are omitted. A model identifier changed by redaction is rejected. The complete redacted preparation snapshot is an artifact; the immutable run binding stores its digest and action. These fingerprints are provenance, not permission tokens.

The coordinator currently caps activities at the smaller of the configured ceiling and 128 work steps; both configuration and actual ceiling are recorded. Oversized requests/snapshots fail rather than truncate. A run is queued with an open-ended Prepare / Agent / Collect evidence plan. Required run approval changes queued directly to waitingForApproval before the provider starts. Exact approval consumption precedes launch. Discarding a pending capability cancels it; replaying or substituting a preparation token cannot launch a second run. Declined, expired, stale or revoked authorization does not run the provider.

Execution uses a structured watchdog with 100 ms checkpoints, a monotonic deadline, and the exact policy/requester revision frozen at preparation. Quiet providers are cancelled on authority loss or policy replacement as well as timeout. Baseline/final repository capture is optional for projects without a repository; when configured, failure prevents success. The provider stream must start once, carry the same identity and contiguous sequence numbers, obey activity/message/output limits, finish activities exactly once and emit a schema-valid final response matching an observed complete message. Read-only runs reject file-change activities. Events or transport errors after a completed event still fail the run; clean stream termination is required.

Only generated activity labels enter progress. Complete messages cross the redactor before trace/artifact persistence; provider responses remain interpretation, and repository observations remain observed evidence. Output above the 64 KiB trace bound becomes an artifact. Final output is published after required repository collection and is the last output artifact of a successfully completed run. A completed run state is committed only after all stages and final evidence are durable; an artifact alone is not success. The returned execution capability can cancel only its own run. No numerical overall progress is invented.

Failure/cancellation awaits a separate uncancelled terminal write. Failure text uses fixed codes, never raw provider, SQL or system diagnostics. If storage cannot confirm terminalization, the result exposes no confirmed state and requires recovery before another preparation. On a regressed wall clock, terminal cleanup reuses the latest recorded lifecycle timestamp rather than inventing a later time. Evidence failure does not prevent an otherwise possible interrupted-run state update.

Before preparing, the lease owner performs keyset-paged recovery of all nonterminal runs in the project, including older environments and runs beyond the normal history page. It preserves terminal/foreign-project history and marks interrupted runs failed with completion explicitly unverified. A missing historical evidence binding is not synthesized. Corrupt bindings or unavailable persistence fail recovery. No provider session is resumed, no historical action is re-executed, and P1-11b adds connection cancellation and a separate helper process lease so another run cannot overlap unreaped helper work. Shared coordinator tests execute with fake providers on Mac and iPhone; actual Codex process execution remains Mac-only. See [coordinator validation](../Development/p1-11a-validation.md).


## Implemented signed native execution (P1-11b)

`CodexHostExecutionProvider` implements the coordinator's private provider boundary over a dedicated signed XPC connection. It sends an immutable request containing only exact identity, selected directory/executable, sanitized instructions/task, optional model, bounded limits and output schema. Access is always the existing read-only Codex permission profile; the wire type has no arbitrary arguments, shell command or access-escalation field. The native caller must keep the selected directory's security-scoped access grant alive until service shutdown.

Both directions use the existing bundle/team signing requirements. The helper resolves the directory again and compares its physical resource fingerprint before accepting one run per connection. Versioned start/next/cancel messages are bounded to 2 MiB; replies contain one event at a time, with exact run/cursor checking. The queue allows at most 64 events and 2 MiB of serialized observations; overflow is explicit and cancels provider work. These private Mac wire observations are still untrusted and potentially sensitive: they never enter a UI, log, database or mobile response without the coordinator's redactor. Host validation does not replace coordinator validation.

A helper-side project lock in the fixed private application-support directory spans execution through process cleanup, independently of the main app's operational-container lease. Losing the app connection cancels the run and any pending event reply. The helper awaits the provider, which owns subprocess termination/reaping, before releasing its lease. After a main-process crash, a fresh owner can mark old runs interrupted, but a new helper run still cannot overlap a prior provider that has not finished cleanup. There is no provider session resumption or action replay.

`NativeRunService` is the Mac application's public service boundary. Preparation/execution values have no public initializer or wire decoder; only the service produces them. The service creates separate scoped agent and local reviewer authorities with finite lifetimes, exposes explicit review of the displayed action/sequence, and routes start through the coordinator. It also exposes current run/progress/history and sanitized trace/artifact reads bound to the exact agent and environment. Missing/foreign bindings and denied evidence reads fail closed. The trusted configuration owner must install policy updates so active watchdogs observe them; neither a model nor the mobile protocol may call native reviewer/policy methods. This service is not a model-facing tool API.

The actual signed connection has an ordinary account-independent integration test. An explicit native smoke run also exercised the existing Codex login, read one synthetic file, verified exact output and an observed completed command, confirmed unchanged source and persisted completion. The live probe is kept in ignored validation output and is not required by ordinary tests. See [bridge and native service validation](../Development/p1-11b-validation.md).


P1-13a adds a `RepositoryAccess` overload to the native service. It binds the registration's exact project, retains the read-only folder grant until shutdown completes and records the directory plus registration identity/revision in sanitized run-input provenance. The operating-system bookmark is private to the native registry and is never copied into the run snapshot. Direct native callers also record their selected directory. See [repository access](repositories.md).
