AgentDesk — Final Architecture

1. Product Vision

AgentDesk is a local-first native Apple agent-management platform for QA, AQA, coding, debugging, documentation, project knowledge, testing, bug investigation, engineering workflows, and general technical work.

It is not a chatbot wrapper.

It should feel closer to a combination of:

* Xcode
* Linear
* Raycast
* GitHub Actions
* an agent observability platform
* a QA management system
* a workflow/orchestration system

The primary application runs on macOS and is the execution authority.

An iOS companion application allows secure monitoring, review, approvals, and limited control from an iPhone.

The eventual experience should allow the user to issue tasks such as:

Handle QA for B2C-1234

or:

Investigate this Playwright failure

or:

Implement automation for these acceptance criteria

AgentDesk then coordinates the required agents, tools, project memory, repositories, plugins, MCP connections, databases, tests, evidence, and approvals.

12. Temporary Context vs Permanent Memory

AgentDesk must distinguish:

Run Context

Information relevant to one execution.

Evidence

Observed technical information from a run.

Project Memory

Reusable confirmed project information.

Requirement

Versioned authoritative expected behavior.

Bug Registry

Known defects and external ticket associations.

Agents may suggest memory changes.

They must not silently rewrite authoritative project requirements.

13. Requirements Versioning

Requirements are immutable after creation.

If a requirement changes:

requirement.v1.json
requirement.v2.json
requirement.v3.json
current.json

Never overwrite v2 to create v3.

Example:

{
  "requirementId": "manual-review-to-closed",
  "currentVersion": 3,
  "currentFile": "requirement.v3.json"
}

Each version contains metadata such as:

{
  "id": "manual-review-to-closed",
  "version": 3,
  "status": "active",
  "supersedes": 2,
  "description": "...",
  "preconditions": [],
  "rules": [],
  "acceptanceCriteria": [],
  "validationRules": [],
  "expectedBehavior": {},
  "environmentScope": [],
  "references": [],
  "changeReason": "...",
  "createdAt": "..."
}

53. Mandatory Duplicate Detection

Before creating any bug ticket:

Gather evidence
 ↓
Determine failing behavior
 ↓
Determine root behavior
 ↓
Check downstream reachability
 ↓
Load current requirements
 ↓
Search Bug Registry
 ↓
Compare possible matches
 ↓
NEW / DUPLICATE / POSSIBLE_DUPLICATE / RELATED

Do not compare only title text.

Compare:

* root behavior
* endpoint
* module
* component
* validation field
* statuses
* status transitions
* expected behavior
* actual behavior
* HTTP status
* application errors
* persisted DB state
* requirement
* affected scenarios
* environment/region

Use deterministic fingerprints first.

Use Codex semantic analysis only when needed.

Short and specific.

Always include when known.

Only when setup/state matters.

* chronological
* reproducible
* concise
* evidence-based

* endpoint
* IDs
* statuses
* currency
* filters
* payload values

	1	iPhone enters Reconnecting.
